# LandLordService: правила разработки

## Продуктовые решения

- Ничего не придумывать за владельца проекта. Пользователь определяет концепции
  и бизнес-правила, агент реализует согласованные детали.
- Не превращать предположения в требования, поля БД, вычисления или интерфейсы.
  Неясности записывать в `docs/requirements.md` и задавать вопросы.
- Обычные технические детали реализовывать самостоятельно в рамках задачи.
- UI согласован: Tabler + Vue + Symfony API для основного приложения,
  Tabler + Twig для части серверных страниц. Начальный дизайн разрешён.
- Текущая БД является тестовой; пользователь разрешил тестовые данные.
  `admin@example.com` является техническим тестовым аккаунтом.
- 2FA пока отложена. Материал: `docs/two-factor-authentication.md`.

## Технологии и архитектура

- Локальная разработка в Docker Compose: PHP-FPM, Nginx, PostgreSQL, Symfony.
- Использовать актуальные стабильные версии. Проверять официальные источники,
  совместимость и доступность образов. Не заменять их на beta/RC незаметно.
- Фиксировать зависимости lock-файлами, не редактировать `vendor/`.
- Структуру БД и разовые преобразования данных изменять только версионированными
  миграциями Doctrine. Не использовать `doctrine:schema:update/create/drop`,
  ручной SQL-DDL или создание таблиц в коде приложения и init-скриптах.
- Основной интерфейс: Vue + TypeScript + Tabler, сборка Vite. Проектировать
  mobile-first, этот же клиент упаковывается в Capacitor.
- Twig использует те же CSS-ресурсы Tabler. Какие бизнес-разделы делать на Twig,
  определяет пользователь; техническая страница состояния не задаёт эту границу.
- Маршруты `/api/*` обслуживает Symfony, `/server/*` обслуживает Twig.
  Остальное приложение обслуживает Vue с hash-маршрутизацией для web и Capacitor.
- HTML-оболочку web отдаёт Symfony для штатной панели отладки в dev.
  JS и CSS отдаёт Nginx; статическая сборка Capacitor не содержит панели.
- Не дублировать бизнес-логику в Vue и Twig: выполнять её в сервисах Symfony.
- Для локальных Node-команд использовать `docker compose run --rm --no-deps node`.
- Сборка Android требует согласованного appId и HTTPS API; не подменять
  локальную сборку клиента открытием удалённого сайта через `server.url`.
- Бизнес-операции и проверки прав выполнять на сервере. Пользователь может
  совмещать несколько ролей; точную матрицу доступа согласовать отдельно.
- Не реализовывать начисления, индексацию, распределение коммунальных расходов
  и сопоставление платежей без согласованных правил и примеров.
- Импорты выписок должны быть идемпотентными в том числе при пересечении
  периодов разных файлов. Формат и ключ операции согласовать по образцам.
- Для денежных расчётов не использовать float. Точность, валюты и округления
  согласовать перед реализацией расчётов.

## Работа с кодом

- Перед каждой задачей перечитывать относящиеся к ней файлы, сохранять правки
  пользователя и комментарии. Держать изменения небольшими, DRY и YAGNI.
- PHP: `declare(strict_types=1)`, типизированные аргументы и возвращаемые значения.
- Не создавать абстракции и одноразовые вспомогательные методы без необходимости.
- Секреты хранить только в игнорируемых локальных файлах окружения.
- Основной каталог проекта: `/opt/homebrew/var/www/LandLordService`.
  Git-репозиторий, Dockerfile, Compose и данные PostgreSQL находятся здесь.
- Данные БД находятся в `var/postgresql`, резервные копии в `var/backups`.
  Они исключены из Git и Docker build context. Не удалять их при перезапуске.
- Не менять файлы родительского проекта Homebrew.
- Не выполнять коммиты, публикацию или развёртывание без соответствующей задачи.
- После изменений выполнять подходящие проверки приложения и Docker-конфигурации.
  Для регрессий применять red/green и проверять конкретный тест.
- Не запускать `lgtm` для LandLordService. Использовать `./bin/check`
  и подходящие адресные проверки Symfony/Vue.
- Перед завершением проверять итоговые изменения и сообщать о недостающих
  решениях, ограничениях проверки и существенных рисках.
