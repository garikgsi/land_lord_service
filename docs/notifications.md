# Уведомления

Системный модуль добавлен вне исходного плана. Пользовательская приёмка ещё не выполнена.

## Первые события

Получатели определяются полем roles в notification_types. По умолчанию активные незаблокированные пользователи с ROLE_LAWYER получают:
- contract.expiry — окончание договора;
- contract.indexation — дата индексации и последующие периодические напоминания, если включены.

Совмещение ролей сохраняет право получения. При исходных настройках администратор без роли юриста в эту рассылку не включается. Для окончания используется effectiveEnd: ранняя дата
аннулирования заменяет expiryDate. Отменённый до начала договор не уведомляет.

Срок формирования берётся из notification_types.days: по умолчанию 30 точных дней.
Настройки перечитываются перед генерацией; выключенный тип или пустые роли не создают уведомлений.
Фоновая проверка идёт каждую минуту. Пропущенная проверка наверстывается, пока дата
исполнения ещё не прошла; договор, заведённый внутри настроенного окна,
тоже получает уведомление. Повтор не создаёт дубль по (user_id, deduplication_key).
Ключ содержит тип, ID договора и дату события. Настройка периодичности не меняет
арендную плату. При изменении исходного договора уже отправленный текст не
переписывается; для другой даты создаётся другое событие.

## Напоминания технарям о показаниях

- Тип meter.reading, получатели — активные незаблокированные пользователи с
  ROLE_TECHNICIAN, включая совмещённые роли. Администратор без этой роли не получатель.
- За 7 календарных дней до срока. Дата рассчитывается по общему графику объекта
  либо собственному дню прибора; для короткого месяца используется последний день.
- Одно сообщение на объект и конкретную дату срока. Другая дата или другой объект
  образуют отдельное сообщение. Внутри — количество приборов по каждой Unity.
  Учитываются приборы самого объекта и его Space, в том числе неактивного Space,
  если установка сохранена.
- Только установленные приборы без показаний с датой снятия в соответствующем
  месяце. Снятые и уже передавшие показания исключены. use_meter=false не снимает
  обязанность с ранее установленных приборов. Пустой результат не уведомляет.
- Пропуск запуска наверстывается в пределах настроенного окна до срока, включая сам срок.
  Проверяется и начало следующего месяца: например, срок 1 марта напоминается
  22 февраля. После срока устаревшее напоминание не создаётся.
- Дедупликация: пользователь + meter.reading + ID объекта + дата срока.
  Количества — снимок на момент создания; уже созданное сообщение не переписывается
  при последующем вводе показаний. Прочтение остаётся отдельным действием пользователя.
- due_date — дата срока передачи; сообщение входит в личный календарь и ведёт
  в карточку объекта. Каналы и доставка общие с остальными уведомлениями.

Пример сообщения:

    Объект: Торговый центр.
    Срок передачи показаний: 25.03.2027.
    Счётчики без показаний за 03.2027:
    Вода — 5
    Электричество — 5

Отдельных уведомлений на каждый из этих десяти приборов не создаётся.

## Хранение и доступ

notifications: id, user_id, kind, title, message, source_path, deduplication_key,
due_date, created_at, read_at. Личное сообщение принадлежит одному пользователю;
даже администратор через этот API не читает и не меняет чужие сообщения.
Создание выполняет NotificationService::notify(), публичного POST нет.
Текст обычный, без HTML; ссылка только на внутренний маршрут приложения.

GET /api/notifications — по 20 записей, новые первыми; query, status=all|unread.
GET /api/notifications/unread-count — личный счётчик.
GET /api/notifications/{id} — сообщение без изменения статуса.
PUT /api/notifications/{id}/read — идемпотентная отметка прочтения.
PUT /api/notifications/read-all — отметить все свои сообщения.
GET /api/notifications/calendar — свои сообщения с dueDate; диапазон start/end,
начало включительно, конец исключительно, не более 370 дней.
Открытие страницы сообщения вызывает отдельную отметку прочтения.
Счётчик Pinia обновляется после прочтения, при фокусе/возврате сети и раз в 30 секунд;
при выходе из аккаунта очищается, старый ответ не переносит счётчик между аккаунтами.

due_date — дата исполнения, а не дата создания уведомления. Сообщение остаётся в календаре после прочтения: синий — новое уведомление,
зелёный — «Прочитано / исполнено» (заполнен read_at).
Календарь объединяет общие события договоров и личные уведомления; это разные
записи. При совпадении даты они могут отображаться рядом.

## Каналы

Запись в notifications сохраняется всегда. notification_deliveries хранит
отдельную доставку каждого выбранного канала: notification_id, channel, status,
attempt_count, next_attempt_at, locked_until, sent_at, last_error.
Уникальна пара (notification_id, channel). Это техническая очередь, не история
изменений бизнес-сущностей; уведомление неизменно, меняется только read_at.

- db: сообщение уже сохранено и доступно интерфейсу, доставка сразу sent.
- email: готов адаптер Symfony Mailer с существующими MAILER_DSN/MAIL_FROM.
- push: предусмотрен отдельный адаптер; провайдер и регистрация устройств ещё
  не реализованы. Сообщение получает deferred, а не фиктивное sent.

По умолчанию NOTIFICATION_CHANNELS=db и NOTIFICATION_EMAIL_ENABLED=0.
Для новых писем после настройки SMTP:
NOTIFICATION_CHANNELS=db,email и NOTIFICATION_EMAIL_ENABLED=1.
Нельзя считать null://null реальной отправкой. Смена каналов не рассылает заново
ранее созданные DB-сообщения. Тесты не отправляют настоящую почту или push.

Статусы: pending → processing → sent, failed или deferred.
Атомарное получение работы использует FOR UPDATE SKIP LOCKED и пятиминутную аренду.
После аварии просроченная аренда подхватывается другим запуском.
Ошибки повторяются до 5 попыток с задержками 1, 5, 15 и 60 минут.
Ненастроенный канал и неактивный получатель откладываются без расхода попытки.
После настройки: app:notifications:deliver --retry-deferred.
Внешняя доставка имеет семантику at-least-once: при потере ответа SMTP или аварии
после отправки возможен повтор. Уникальный ключ гарантирует отсутствие дублей
самих сообщений и строк очереди, но не exactly-once у внешнего провайдера.

Интерфейс NotificationSenderInterface отделяет канал от предметного генератора.
Для реального push нужно заменить PushNotificationSender, подключить провайдера
и отдельную защищённую регистрацию устройств в рамках мобильного этапа.

## Запуск

Docker Compose содержит сервис notifications с backend/bin/notifications-worker.
Он запускает генератор и доставку раз в минуту. Отдельный cron на хосте не нужен.

Локально после миграций:

    docker compose up -d --build notifications

Разовая проверка генерации:

    docker compose exec -T php php bin/console app:notifications:generate

Доставка очереди (может отправить реальные письма, если канал включён):

    docker compose exec -T php php bin/console app:notifications:deliver --limit=100

Production bin/deploy останавливает worker вместе с PHP/Nginx до резервной копии
и миграций, затем запускает его после готовности новой версии. При неудаче миграции
worker остаётся остановленным. Данные очереди входят в обычный дамп PostgreSQL.

Миграция Version20261121150000 создаёт обе таблицы и индексы.
HTML-инструкция: frontend/public/help/users.html, Swagger: /server/api.

## Согласовано для договоров коммунальных поставщиков

Тип supplier_contract.expiry реализован для UnityProviderContract: за настроенное число дней (по умолчанию 30) до expiry_date уведомляются роли из notification_types (по умолчанию ROLE_LAWYER). Событие попадает в личный календарь, защита от повторной генерации общая. Приостановка договора не отменяет контроль истечения. ObjectUnityProvider остаётся связью поставщика и коммуникации объекта, не источником даты договора.

## Настраиваемые типы: актуальное поведение с 22 ноября

Прежний календарный месяц заменён точным числом дней (согласовано владельцем). Таблица notification_types: id, name, days, roles JSONB, is_active. По умолчанию: окончание аренды — 30 дней/ROLE_LAWYER, индексация — 30/ROLE_LAWYER, показания — 7/ROLE_TECHNICIAN, окончание договора коммунального поставщика — 30/ROLE_LAWYER. Каждый генератор получает свежие настройки из БД, без кеширования ORM или процесса. Любая из выбранных ролей подходит; активность и блокировка пользователя сохраняют значение. Выключенный тип или пустой список ролей дают ноль новых уведомлений. 0 дней означает день события. Старые сообщения и очередь доставки не стираются.

Настройки доступны администратору и директору: /settings/notification-types, API GET /api/notification-types, GET/PUT /api/notification-types/{id}. Создание/удаление системных типов через UI не предусмотрено: новый тип требует генератора. roles здесь задаёт получателей, а не назначает пользователям права.

Генератор UnityProviderContractNotificationService подключён к app:notifications:generate: контролирует expiry_date договоров поставщиков, включая приостановленные, сохраняет дату исполнения для календаря, ссылается на /unity-provider-contracts/{id}. Повторная генерация идемпотентна. Изменение days или roles применяется при следующем запуске, перезапуск контейнера не нужен. История даты/суммы индексации не переносит фактическое изменение платежа в будущее.


## Начавшийся неподписанный договор аренды

Тип contract.unsigned (notification_types.id=5) создаёт напоминания юристам и директору по умолчанию. days=7 — интервал повторения, а не срок до события; минимум 1 день. API возвращает timing=repeat (для прежних типов timing=lead), поэтому интерфейс подписывает поле «Повторять через, дней». Настройки и получатели читаются заново при каждом запуске.

Расписание начинается с contract_date и повторяется через days календарных дней, пока договор действует и is_signed=false. До начала аренды, после окончания/аннулирования и после подписания новых напоминаний нет. Ключ contract.unsigned:{id}:{дата_текущего_периода} уникален для получателя; повторные дневные запуски не дублируются. При пропуске недель формируется только текущее напоминание. Прочтение сохраняет статус старого сообщения, а в следующем периоде приходит новое. Совмещённые роли не удваивают сообщения; заблокированные и неактивные пользователи исключены. Роль администратора сама по себе не подписывает на сообщения юриста/директора.

Сообщение содержит договор, дату начала аренды, объект и арендатора, ведёт в карточку договора. Дата исполнения — дата текущего повторения; календарь и цвет прочитанного сообщения используют общий механизм. Каналы db/email/push задаются прежней общей конфигурацией; реальный push по-прежнему относится к мобильному этапу.
