# Пользователи приглашения и авторизация

## Создание и активация

Администратор указывает имя и email. Фамилия, телефон, должность, аватар
и сочетание ролей необязательны. Имя обязательно для новых записей и изменения
профиля; у старых технических записей оно может отсутствовать до заполнения.
Поля задания пароля в административном интерфейсе и прямой API установки
чужого пароля удалены.

Новая запись создаётся с `active=false`. Пользователь получает письмо со ссылкой
на публичный экран `/activate?token=...`, проверяет данные, задаёт или генерирует
пароль и сохраняет профиль. Только после успешного сохранения сервер хеширует
пароль, активирует запись и погашает приглашение. Затем пользователь входит
в систему. До активации вход, обычный Bearer API и восстановление пароля недоступны.

В форме активации пользователь меняет имя, фамилию, телефон, должность и фото.
Email привязан к приглашению, роли и блокировку пользователь себе не назначает.
Круглый аватар открывает выбор изображения и сохраняет фото сразу; это действие
само по себе не активирует запись. После активации изменение профиля обычного
пользователя выполняет администратор.

Приглашение содержит случайный токен с энтропией 256 бит; в БД хранится SHA-256.
Срок по умолчанию — 24 часа (`USER_INVITATION_TTL=86400`). У пользователя одна
действующая ссылка. Успешная повторная отправка заменяет её; при ошибке доставки
транзакция откатывается, предыдущая ссылка остаётся действующей до своего срока.
Повторные письма ограничены тремя запросами на пользователя за 15 минут.
Блокировка и изменение почты/ролей отзывают ссылки; для ожидающего активации
пользователя администратор затем отправляет новое приглашение.

При отключённом или недоступном SMTP создание возвращает 201 с сохранённой
неактивной записью, `invitationSent=false` и предупреждением. Повторно создавать
пользователя не нужно: после настройки почты нажать повторную отправку.
Сама повторная отправка при недоступной почте возвращает 503.

## Права на изменение пользователей

Совмещаемые роли: `ROLE_ADMIN`, `ROLE_ACCOUNTANT`, `ROLE_TECHNICIAN`,
`ROLE_LAWYER`, `ROLE_DIRECTOR`. Индивидуальные разрешения поверх ролей не вводятся.

`ROLE_SUPER_ADMIN` принадлежит только системной учётной записи, создаваемой
миграцией при инициализации системы (`admin@example.com`). Назначение и снятие
этой роли запрещены через API, интерфейс и CLI для всех, включая её владельца.
В форме она входит в общий список ролей как «Суперадмин», выделена фиолетовым
цветом и показана с отключённым флажком.

Обычный пользователь видит свой профиль и сообщение «Для изменения данных
обратитесь к администратору системы». Администратор меняет себя и обычных
пользователей. Суперадминистратор дополнительно меняет все данные администраторов,
назначает и снимает `ROLE_ADMIN`, блокирует их вход. Проверки действуют для профиля,
email, ролей, блокировки, аватара и административного сброса пароля на сервере.
Повторное приглашение отправляется только на уже сохранённый email.

Никто не может заблокировать собственную запись. В форме блокировка отделена
разделителем Tabler от ролей, для своей записи флажок отключён. Сохранение профиля
доступно после фактического изменения хотя бы одного поля; возврат исходных значений
снова отключает кнопку. Фото сохраняется и удаляется сразу, независимо от формы.
Отмена выбора файла оставляет страницу редактирования открытой.

Создание и редактирование открываются на отдельных маршрутах `/admin/users/new`
и `/admin/users/{id}`. Карточка занимает ширину рабочей области. На широком экране
почта и телефон расположены рядом, роли — в общей строке с переносом при нехватке
места. Короткие поля на мобильном экране располагаются друг под другом.

Имя, почта и телефон проверяются на клиенте и сервере. Пустое/пробельное имя,
некорректный email и неполный телефон блокируют сохранение. Необязательный телефон
можно оставить пустым; заполненный показывается как `+7 (ХХХ) ХХХ-ХХ-ХХ`.
Ошибки отображаются под соответствующими полями.

Последнего активного администратора нельзя лишить доступа.
Права на будущие операции с недвижимостью уточняются при реализации модулей.

## Сеанс

API принимает `Authorization: Bearer <token>`. При входе выдаётся случайный токен
с энтропией 256 бит, сроком действия и безопасным представлением пользователя.
В БД хранится только SHA-256. По умолчанию срок — 8 часов (`ACCESS_TOKEN_TTL`).
Продления пока нет; после истечения нужен повторный вход. Выход отзывает текущий
токен. Изменение email, ролей, блокировки или пароля отзывает все сеансы
и ссылки восстановления/приглашения пользователя.

Vue хранит токен в `sessionStorage`, проверяет через `/api/auth/me` при загрузке
и очищает при 401 защищённого запроса, переводя закрытую страницу на вход.
Прямая очистка сеанса также вызывает переход; ошибка входа остаётся в форме входа,
а запоздалый 401 старого токена не отменяет новый сеанс. Для Android потребуется адаптер Keystore. Открытой регистрации
нет; знание email не позволяет получить или повторно отправить приглашение
через публичный API. 2FA отложена.

## API

| Метод | Путь | Назначение |
| --- | --- | --- |
| POST | `/api/auth/login` | Вход активного пользователя, email/password |
| GET | `/api/auth/me` | Текущий пользователь |
| GET | `/api/roles` | Справочник ролей: code, label, description, assignable для текущего пользователя |
| POST | `/api/auth/logout` | Отзыв текущего токена |
| POST | `/api/auth/forgot-password` | Публичный запрос восстановления активной записи |
| POST | `/api/auth/reset-password` | Новый пароль по одноразовому reset-токену |
| POST | `/api/auth/invitation` | Данные для активации, JSON token |
| POST | `/api/auth/activate` | token, firstName, password, необязательные lastName/phone/position |
| GET / POST / DELETE | `/api/auth/invitation/avatar` | Просмотр/загрузка/удаление фото по заголовку X-Invitation-Token |
| GET | `/api/admin/users` | Администратор, page/query/state |
| POST | `/api/admin/users` | Создание неактивной записи и отправка приглашения |
| GET | `/api/admin/users/{id}` | Профиль по ID для отдельной страницы редактирования |
| PUT | `/api/admin/users/{id}` | Изменение разрешённой записи без установки пароля |
| POST | `/api/admin/users/{id}/invitation` | Повторная отправка приглашения |
| POST | `/api/admin/users/{id}/password-reset` | Отправка ссылки активному пользователю с проверкой прав |
| POST / DELETE | `/api/admin/users/{id}/avatar` | Изменение фото с проверкой прав |
| GET | `/api/users/{id}/avatar` | Фото владельцу или администратору |

Список: 20 записей на страницу, поиск по имени/фамилии/почте/телефону/должности,
`state=all|active|blocked|pending`. Поле `active` обозначает завершённую активацию;
`blocked` хранится отдельно и запрещает доступ даже активной записи.
В JSON не возвращаются пароли, хеши или токены приглашений.

Названия и описания ролей приходят с `/api/roles`; Pinia загружает справочник один раз
за сеанс и очищает при выходе. `assignable` отражает права текущего пользователя:
системная роль всегда недоступна, `ROLE_ADMIN` назначает только суперадминистратор.
Описания предметных ролей обозначают их назначение; доступ к будущим модулям
будет согласован отдельно. Этот флаг не заменяет серверную проверку операций.

## Фото профиля

Круглый аватар показывает фото либо инициалы имени и фамилии; без имени и фото
отображается значок пользователя. Фото хранится в приватном `backend/var/avatars`:
JPEG/PNG/WebP, до 2 МБ, не более 4096×4096. В обычной форме и на экране активации
загрузка/удаление фото сохраняются сразу, независимо от остальных полей.
Для новой записи в форме администратора фото загружается после создания записи.

## SMTP и восстановление

Настройки в корневом игнорируемом `.env`:

```dotenv
MAILER_DSN=smtp://USERNAME:PASSWORD@SMTP_HOST:587
MAIL_FROM=noreply@your-domain.example
APP_FRONTEND_URL=http://127.0.0.1:18080
USER_INVITATION_TTL=86400
PASSWORD_RESET_TTL=3600
```

Использовать параметры своего SMTP-провайдера. Специальные символы логина/пароля
в DSN кодируются как URL-компоненты; секреты не добавляются в Git.
После изменения настроек выполнить `docker compose up -d --wait php`.
При `null://null` письма не отправляются, Mailpit не добавлен.

Восстановление пароля доступно только активной незаблокированной записи.
При настроенной почте публичный ответ одинаков для существующих и неизвестных
адресов. Ссылка восстановления одноразовая, по умолчанию действует час;
новый запрос заменяет предыдущий. Сброс пароля не активирует ожидающую запись.

## База и проверки

Таблицы пользователей и токенов создаёт `Version20261119105831`, имена добавляет
`Version20261119122932`. Миграция `Version20261119144813` добавляет активность
и приглашения; существующие записи с заданным паролем сохраняют активность.
`Version20261119152136` закрепляет системную роль за согласованной технической
записью, `Version20261119171000` создаёт её при чистой установке и убирает
системную роль у остальных записей. Все изменения схемы и разовые преобразования
выполняются только миграциями.

Миграция создаёт системную запись без пароля и с `active=false` в новой БД.
Существующая техническая запись при обновлении сохраняет пароль и профиль.
CLI-команда только инициализирует уже созданную миграцией запись: имя обязательно,
пароль запрашивается скрыто. Повторная инициализация запрещена:

```sh
docker compose exec php php bin/console app:user:initialize-admin 'Имя администратора'
```

Это первоначальная настройка системы. Обычных пользователей администратор
создаёт через приглашения. Автотесты используют отдельную БД с суффиксом `_test`
и почтовую заглушку; внешние письма из тестов не отправляются.
