# Приборы учёта

Реализованы коммуникации Unity, поставщики UnityProvider и связи поставщиков с
объектами. Несколько поставщиков одной коммуникации допустимы. Номер и даты
договора с поставщиком не добавлялись.

## Карточка и установка

Раздел /meters; отдельные страницы создания и редактирования. Вкладки:
«Основное», «Показания», «Поверки». На объекте и Space список находится во
вкладке «Счетчики» объекта и «Счётчики» помещения. У помещения также вкладки «Основное» и «Договоры».
Поставщики объекта вынесены в отдельную вкладку «Поставщики».
Из неё можно выбрать существующего поставщика либо создать нового в модальной
форме (общая UnityProviderForm со страницей справочника). Новый поставщик
автоматически добавляется к объекту; при неудаче привязки остаётся выбранным
для повторного добавления. Создание поставщика не требует счётчика.
При первом создании требуется место установки: объект либо помещение.
Снятие очищает текущую связь, сохраняя прибор, показания и историю поверок.
Перенос выполняется в транзакции; две одновременные установки запрещены также
триггером PostgreSQL. Истории мест установки нет по согласованным требованиям.

createDate вводится как дата производства, не дата создания в БД. Начальное
показание относится к этой дате. Заводской номер необязателен. Интервал поверки
обязателен. Последняя поверка определяется максимальной датой истории;
при отсутствии поверок срок отсчитывается от производства. Предельный день
включён: предупреждение возникает со следующего дня. Просроченный прибор можно
установить; предупреждение остаётся в карточке и списке до актуальной поверки.

## Показания и потребление

Целые неотрицательные значения в пределах PostgreSQL INT. Дубликат момента
снятия запрещён; ошибку исправляют в исходной записи. Ввод задним числом
проверяется относительно предыдущего и следующего показаний, а также
начального значения. Потребление рассчитывается до пагинации списка:
разница соседних значений за фактический интервал. Для первого — от
начального значения и даты производства. Истории исправлений и удаления
показаний нет, тарифы и стоимость не рассчитываются.

## График и календарь

Срок наследуется от объекта (исходно 25), индивидуальный readingDay может
замещать его. Пустое индивидуальное поле означает наследование. Число 29–31
в коротком месяце переносится на последний день. Снятые приборы не попадают
в график; состояние Space само по себе не отменяет передачу показаний.

В календаре сроки передачи оранжевые, переданные вовремя — зелёные, переданные с просрочкой и поверки — красные.
Технарям за 7 дней до срока формируются личные уведомления по объекту и одной
дате срока, с количеством счётчиков по коммуникациям. Учитываются только
установленные приборы без показаний за нужный месяц; подробности —
[notifications.md](notifications.md).

Права уточнены:

- METER_EDIT — только администратор: реквизиты уже созданных приборов, поверки,
  индивидуальный график, коммуникации, поставщики и связи поставщиков с объектами.
- METER_READING_EDIT — администратор и технарь: внесение и исправление показаний.
- METER_INSTALL — администратор и технарь: создание/регистрация нового прибора
  с установкой, установка существующего, снятие и перенос. Исходные реквизиты
  заполняются при создании; повторное редактирование карточки — администратор.
- При создании технарь наследует общий график объекта; собственный readingDay
  не показывается в форме и запрещён сервером для этой роли.
- Остальные роли просматривают; совмещённые роли складывают права. Общие
  настройки объекта остаются недоступны самой роли технаря.

Месяц и своевременность определяются датой снятия. Срок 25-го:
снято 23-го или 25-го — вовремя; снято 26-го — с просрочкой. День внесения
в систему и создания записи в БД не участвует. Прежняя интерпретация о
времени внесения отменена; новая колонка для этого не нужна.

Достаточно показания с датой снятия в месяце, чтобы закрыть месяц. Если есть
показание не позже срока, месяц исполнен вовремя; если все показания после
срока — исполнен с просрочкой. В API readingSubmittedLate отделяет исполнение
с опозданием от отсутствующих показаний (readingOverdue). В календаре и списке
опоздание показано красным с явным текстом. Изменение даты снятия пересчитывает
результат по актуальной записи, без истории исправлений.

Общий день передачи и настройки объекта технарю менять запрещено по решению
владельца. Прежний доступ администратора и юриста к объекту сохранён; вопрос закрыт.

## Хранение и проверка

Миграция Version20261121160000 переносит имеющуюся последнюю поверку в историю,
добавляет полные архивные версии Unity, UnityProvider и Meter с valid_from /
valid_to. Текущая версия остаётся только в основной таблице; первое создание
не порождает архивную строку. Исправления показаний не архивируются по
отдельному согласованному исключению.

API описан в Swagger /server/api; пользовательская инструкция — /help/users.html.
Модуль доступен локально, ждёт проверки владельца вместе с уведомлениями.

## Поставщики и коммуникации объекта

UnityProvider — общий справочник id/name. Поставщик может обслуживать сколько
угодно коммуникаций и использоваться на разных объектах. На каждом объекте
отдельно задаются ObjectUnityProvider(objectId, unityId, unityProviderId).
Один поставщик на А может обслуживать воду и электричество, на Б — только воду.
Несколько поставщиков одной коммуникации на одном объекте допустимы; точный
повтор тройки повторно не создаётся. Поставщик может быть создан без счётчиков
и без заранее выбранной коммуникации.

В установке общего счётчика необязательное поле «Поставщик». В списке только
поставщики его объекта и коммуникации. В API передаётся objectUnityProviderId —
ID связи на объекте, не ID глобальной карточки. Пустое поле сохраняется как NULL.
У счётчика Space поставщик не выбирается. При переходе в Space/снятии привязка
исчезает. Для изменения типа счётчика сначала очищается несовместимый поставщик;
для удаления связи поставщика — сначала очищается её выбор у счётчиков.

Version20261121170000 переносит прежний глобальный тип в связи на объектах,
сохраняя их ID. Поставщиков у существующих счётчиков автоматически не назначает.
Старый unity_providers.unity_id становится nullable и остаётся техническим
носителем прежних сведений, в том числе для сохранения зеркальных _history.
В новых карточках он пуст, в бизнес-правилах/API не используется. Исторические
поля не удаляются и не заменяются выдуманными значениями. Откат запрещён,
если новая структура уже содержит несколько коммуникаций одного поставщика,
назначения счётчиков или нового поставщика без типа, не представимые старой схемой.


### Навигация сущностей: уточнение 23 ноября

- Основной маршрут записи и переход из строки её реестра открывают форму редактирования с прежними проверками прав. Нередактируемое представление показывать только в явно указанных владельцем местах, преимущественно модально для сторонней сущности. Не подменять им основной маршрут и не менять структуру меню.
- Счётчик: /meters/:id — форма с вкладками; /meters/:id/edit перенаправляет на основной адрес с сохранением query. В «Коммуналке» объекта бейдж открывает модальное превью; его кнопка «К счетчику» ведёт на основной маршрут. Возврат и сохранение используют исходный returnTo, без промежуточной страницы просмотра.
