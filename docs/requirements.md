# Требования LandLordService

Источник: описание владельца проекта от 19 ноября 2026 года.
Это фиксация запроса, а не утверждённая схема данных.

## Подтверждено пользователем

- Есть несколько объектов недвижимости с торговыми или офисными зданиями.
- По уточнению заказчика фиксированных помещений на объекте нет. `Space`
  выделяется из общей площади объекта для аренды. Состав полей и вопросы
  по новой модели: [domain-model-review.md](domain-model-review.md).
  Уточнение 34–36 заменяет прежнее правило занятости только по датам договоров:
  Space создаётся вместе с первым договором и сразу резервирует площадь,
  даже если начало аренды впереди. При перезаключении Space сохраняется,
  при расторжении становится неактивным. По уточнению 37–39 резерв снимается
  на следующий день после окончания без нового договора или расторжения;
  перезаключение на прежнем Space возможно только без перерыва.
- Коммуникации могут иметь приборы учёта. Нужно вносить показания, рассчитывать
  потребление и вести график передачи показаний. Ответы 56–57: разница показаний
  за фактический интервал без искусственной разбивки пропущенных месяцев.
  На текущем этапе только потребление, без тарифов, стоимости и коммунальных начислений.
- Есть поставщики коммунальных услуг и договоры с ними.
- Несколько собственных юридических лиц выступают владельцами или
  субарендаторами и оплачивают коммунальные и прочие услуги объектов.
- Есть договоры аренды. Контролируем сроки и планируем повышение арендной платы.
  Продления отдельно не реализуются. Уточнение 21 ноября: индексация меняет
  текущий договор с сохранением прежней версии (см. ниже).
  Юрист может аннулировать договор указанной датой.
- Арендаторы: юридические лица, ИП и физические лица.
- Нужен реестр договоров по объектам и датам истечения.
- Сальдо аренды — по каждому договору и суммарно по арендатору.
  Уточнение 52: импорт выписок пока отложен целиком. Бухгалтерия вводит платежи
  вручную в конкретный договор через интерфейс, в том числе задним числом.
  При возвращении импорта в объём работ потребуется идемпотентность.
- Арендную плату начисляем в этой системе. Формулы, периоды и другие правила
  начислений согласуются поэтапно. Все договоры авансовые: 5-го числа текущего
  месяца неоплата по действующим договорам становится задолженностью.
  Ответы 58–60: директор задаёт итоговую сумму к оплате за месяц, включая 0
  (каникулы), не дельту. В интерфейсе — скидка, каникулы или корректировка.
  Базовый неполный месяц начисляется пропорционально дням аренды по фактическому
  числу дней в месяце — правило окончательно подтверждено, не предварительное.
  Директор может корректировать любые параметры начисления, включая прошедшие
  и оплаченные месяцы. Изменение начисления меняет сальдо; платежи при этом
  автоматически не переписываются. Итоговое начисление округлять один раз в конце до копеек по
  математическому правилу (HALF_UP), без промежуточного округления дневной ставки. Например, 100,005
  → 100,01. Импорт выписок отложен.
- Для начислений подготовлена contract_accruals и отдельная
  contract_accruals_correction для директорских корректировок. Схема согласована,
  SQL включён в предметные миграции; сервис расчёта ещё не реализован. У начисления может быть несколько корректировок;
  актуальны параметры и итоговая сумма последней записи, включая 0.
  Без корректировок применяется исходное начисление. Корректировки не складываются
  и не являются дельтами. Последняя определяется порядком создания
  (created_at DESC, id DESC); пересчёт базы не затирает её.
- Бухгалтерия заносит платежи, технические сотрудники вносят показания,
  юрист ведёт договоры, администратор имеет полные права, директор смотрит
  аналитику. Один пользователь может совмещать несколько ролей.
- Backend: Symfony, PHP, Nginx, PostgreSQL в Docker.
- Web: адаптивный mobile-first интерфейс с перспективой Android на Capacitor.
- Нужны бесплатная UI-панель, календарь, таблицы и автокомплиты.
- Начальный дизайн выполняется после согласования UI-панели.
- Панель согласована: основной интерфейс на Tabler + Vue + Symfony API.
  Этот же Vue-клиент будет использоваться в Android-приложении через Capacitor.
  Часть функциональности будет на Tabler + Twig; конкретные разделы не определены.
- Концепции и бизнес-правила определяет пользователь.

## Открытые решения

1. UI: конкретные бизнес-разделы на Twig и границы их мобильной доступности
   нужно определить по мере разработки. Архитектура и панель согласованы.
2. Импорт выписок пока вне текущего объёма: ввод платежей ручной по договорам.
   Формат и образцы потребуются только при отдельном возвращении задачи импорта.
3. Начисления аренды выполняются в системе, начинаем с нулевого сальдо.
   Бухгалтерия вводит платёж в конкретный договор; пользователь исправляет
   собственную запись, удалять платёж может только администратор.
   Округление согласовано: итог до копеек, HALF_UP, один раз в конце;
   промежуточная дневная ставка не округляется.
4. Договоры: уточнить цепочку собственник → арендатор → субарендатор,
   роли собственных юрлиц и стороны каждого вида договора.
5. `Space` выделяется из площади объекта; договор содержит `spaceId`.
   Площадь резервируется сразу при создании Space с первым договором. Пересечения периодов договоров одного
   Space запрещены, включая общий день окончания/начала. При изменении площади
   создаются новые Space, прежние сохраняются для истории. При обычном
   перезаключении договора Space остаётся; при расторжении становится неактивным.
6. Аренда: как задать ставку, периоды, сроки платежей, индексацию,
   перерасчёты? Начальное сальдо пока нулевое. Обеспечительный платёж только реквизит,
   без отдельного учёта движения и зачётов.
7. Учёт ресурсов: где установлены счётчики, есть ли общие/вложенные приборы,
   тарифные зоны, замены и сбросы; что делать с помещениями без счётчиков?
8. Коммунальные услуги: сейчас только потребление по показаниям. Тарифы,
   стоимость, коммунальные начисления и распределение не входят в текущий объём.
9. Доступ: права только по операциям или также по объектам и юридическим лицам?
10. Календарь: сроки и события или также дорожки по помещениям/объектам?
11. Мобильный клиент: понадобится ли работа без сети? Сам Capacitor
    не определяет правила офлайн-ввода и разрешения конфликтов.

Вопросы уточняются по мере работы над соответствующим модулем.
20 ноября схема согласована. Пять предметных миграций на 20 таблиц находятся
в `backend/migrations/domain`, зарегистрированы в Doctrine и применены
к локальной development-БД через миграции. Реализованы ORM всех таблиц и API/интерфейс объектов и арендодателей;
остальные предметные API и расчёты пока не реализованы.
Сервер при создании объекта подставляет reading_day = 25, при создании договора —
тип «аренда». Оба столбца обязательны в БД и не имеют SQL DEFAULT.

## Технические предложения, требующие предметного уточнения

- Идемпотентность должна учитывать повторный файл и повторные операции
  в разных выписках с пересекающимися периодами. Хеша файла недостаточно.
  Ключ банковской операции и обработка исправлений зависят от образцов.
- Сальдо складывается из начислений и ручных платежей по договору; начальное
  сальдо на текущем этапе нулевое. Пользователь исправляет собственную запись
  платежа, удаляет платёж только администратор. Автор платежа сохраняется
  для проверки прав. Начальные долг/переплата пока не вводятся.
- Роли можно совмещать. Ограничения на чтение, изменение и объекты ещё
  не определены; перечисленные роли не являются готовой матрицей доступа.

## Пользователи и доступ: согласовано

- Основной идентификатор пользователя: email.
- При создании обязательны имя и email; остальные поля необязательны.
- Дополнительные поля: фамилия, аватар, телефон, должность и набор ролей.
- Роли можно совмещать: администратор, бухгалтерия, технарь, юрист, директор.
  Индивидуальные разрешения поверх ролей пока не нужны.
- Вход через API с Bearer-токеном. Открытой регистрации нет.
- Открытые экраны: вход, запрос восстановления, установка нового пароля.
- Администратор создаёт пользователей по приглашению без задания пароля,
  блокирует обычных пользователей, меняет их email и роли, отправляет ссылки.
- Пользователь по ссылке задаёт пароль и дополняет профиль. Только после
  сохранения учётная запись становится активной. Приглашение можно отправить повторно.
- Обычный пользователь для изменения данных обращается к администратору.
  Администратор меняет свои данные и данные обычных пользователей; изменение
  другого администратора запрещено, включая email, роли, блокировку и аватар.
- Первый администратор: admin@example.com. Пароль задан пользователем отдельно
  и не включается в исходники или документацию.
- SMTP уже есть, его подключение будет отдельной настройкой. Mailpit не добавлять.
- Схему БД и разовые преобразования данных изменять только через миграции.

- Текущая БД тестовая; admin@example.com является техническим тестовым аккаунтом.
- 2FA отложена. Материал сохранён в docs/two-factor-authentication.md.

## Аватар пользователя: уточнение

- Круглый аватар показывает сохранённое фото либо первые буквы имени и фамилии.
- Имя и фамилия добавлены в профиль; для старых записей они могут отсутствовать.
  До их заполнения показывается нейтральный значок пользователя.
- Нажатие на круг открывает выбор изображения. Выбранное фото сохраняется сразу,
  независимо от сохранения остальных полей формы.
- У новой учётной записи фото загружается после её создания.

## Новая предметная модель от заказчика

- Арендодатель — простой справочник `LandLord(id, name)`.
- Первый набор полей объекта: `id`, `square`, `name`, `address`.
  Арендодатель относится ко всему объекту через `landLordId`.
- `Space(id, name, square)` — выделяемая арендуемая часть объекта.
  Вводятся площадь и реквизиты договора, графический план не нужен.
  name по умолчанию генерируется из площади и Renter.name арендатора,
  например «100 кв.м ИП Иванов И.И.». Используется имя арендатора, не арендодателя.
  Пользователь может изменить название вручную; сохраняется введённое им значение.
- Тип договора — обязательный справочник ContractType(id, name), ссылка
  contractTypeId (contract_type_id). Начальные записи: «аренда» (по умолчанию),
  «юр.адрес». Записи создаёт миграция. Оба типа связаны со Space и занимают площадь.
- У договора указаны `id`, `spaceId`, `renterId`, `securityPayment`, `expiryDate`,
  `contractDate`, `contractNum`, `monthlyPayment`, `increaseDate`, `increasePercent`.
  `contractDate` — начало аренды. Добавлено необязательное `annulmentDate` для
  аннулирования указанной датой; дата подписания не требуется.
  В интервью подтверждено: expiryDate обязательна, бессрочных договоров нет.
  increaseDate и increasePercent могут быть NULL только одновременно;
  если индексация задана, заполнены оба поля. securityPayment может быть 0,
  отсутствие обеспечительного платежа не обозначается NULL.
  monthlyPayment — сумма за весь Space за месяц, не ставка за м².
  Арендная плата и обеспечительный платёж — только в рублях.
  Смена арендодателя объекта влечёт перезаключение договора.
  Номер договора справочный, может повторяться; к одному договору нужны
  несколько файлов любых типов до 20 МБ каждый. Исторические договоры,
  Space и показания физически не удаляются. Удалять вложения договора могут
  юрист и администратор.
  Разрешена отмена до начала аренды с сохранением договора
  в истории: он никогда не занимает площадь и не блокирует другие договоры.
- Тип арендатора — отдельный справочник `Ownership(id, name)`; у Renter
  предусматривается обязательная ссылка ownershipId (ownership_id).
  Начальные записи: «Юридическое лицо», «Индивидуальный предприниматель»,
  «Физическое лицо»; заполняются миграцией.
- `Renter`: `id`, `name`, необязательный `inn`. Арендатора можно создать до
  получения ИНН. После заполнения ИНН должен быть уникальным среди арендаторов;
  отсутствие хранится как NULL. Ответ 18 заменяет прежнюю обязательность ИНН.
  `RenterContact`: `id`, `renterId`, обязательное `name`,
  необязательные `lastName`, `patronymic`, `phone`, `email`.
  Контакт допустим без телефона и email.
- `Unity`: `id`, `name`, `useMeter`, необязательная единица измерения (добавлена по интервью).
  useMeter (use_meter) — возможность установки счётчика: без признака поле
  счётчика не показывается; с признаком доступно. Обязательность установки не задаётся.
  Признак разрешено выключать при существующих счётчиках; приборы, данные
  и связи сохраняются. Задания по показаниям по-прежнему зависят от установки.
  `UnityProvider`: `id`, `unityId`, `name`;
  `ObjectUnityProvider`: `id`, `unityProviderId`, `objectId`.
  На объекте допускается несколько поставщиков одного типа коммуникации.
- `Meter`: `id`, `utilityId`, `createDate`, `startRead`, `verificationDate`,
  `verificationIntervalDays`, необязательный справочный `serialNumber`.
  `createDate` — вручную заполняемая дата производства и дата начальных показаний,
  не дата добавления записи в БД. verificationIntervalDays обязателен; показания целые.
  verificationDate — необязательная последняя поверка. При NULL прибор считается
  новым: базой служит createDate. Срок = база + verificationIntervalDays дней.
  Если текущая дата позже срока, прибор невалиден, но его установку разрешаем.
  Постоянное предупреждение в интерфейсе сохраняется до действующей поверки;
  статус вычисляется по датам, отдельный флаг валидности не хранится.
  У счётчика не более одной установки: объект либо Space. При снятии связи
  очищаются, прибор и показания сохраняются. Задания на передачу показаний
  нужны только при наличии установки в момент передачи. Флаг активности
  не вводится. Это уточняет ответ 33. Счётчики независимы, иерархия не нужна.
  Храним только текущее место установки, без истории перемещений.
  История всех поверок нужна: запись содержит id, ссылку на счётчик и дату поверки.
  Комментарий, номер свидетельства и файл поверки не нужны.
- `ObjectMeter` и `SpaceMeter`: `id`, необязательный `comment`, `meterId`.
  В интервью подтверждены `Space.objectId`, `ObjectMeter.objectId` и `SpaceMeter.spaceId`:
  каждый Space принадлежит ровно одному объекту, установки указывают объект или Space.
  Связь объекта с арендодателем подтверждена ранее.
- `MeterReading`: `id`, `meterId`, `meterReadingDate`, `meterRead`.
  Уменьшение показаний запрещено; ввод задним числом и исправление ошибочного
  показания разрешены. Проверять порядок значений относительно соседних записей
  по времени и начального показания. На прибор и момент снятия одно актуальное
  показание. Ошибку исправляют в существующей записи, историю исправлений не хранят.
- График передачи показаний ежемесячный, общий на уровне объекта для его приборов
  и приборов Space. По умолчанию — 25-е число месяца. У отдельного счётчика можно
  задать собственный срок; без него используется график объекта.
- Денежные суммы хранятся в `NUMERIC`; площади и процент также переведены
  на точное десятичное хранение без заданного масштаба. Ответом 61 согласовано
  округление итогового начисления до копеек один раз в конце по HALF_UP,
  без промежуточного округления дневной ставки. Подробности в [разборе модели](domain-model-review.md).
- Поставщики пока остаются с исходными полями, без реквизитов договоров.
- Уточнение 34–36: Space и первый договор создаются совместно, площадь
  резервируется сразу, включая период до начала аренды. При перезаключении
  используется прежний Space; при расторжении он становится неактивным.
  square объекта — полностью сдаваемая площадь. Уточнение 22 ноября заменяет прежнее разрешение превышения: отрицательный остаток запрещён.
  Уточнение 37–39: резерв автоматически освобождается на следующий день после
  окончания без нового договора или после даты расторжения; сама конечная дата
  включена в аренду. Будущее расторжение не освобождает площадь сразу.
  Прежний Space сохраняется только при перезаключении без перерыва;
  после освобождения для новой аренды создаётся новый Space.
  Пересечения периодов договоров одного Space по-прежнему запрещены.
  При изменении площади создаются новые Space, прежние сохраняются для истории.

## Версии и действия с договорами: уточнение от 21 ноября

- Текущее физическое состояние находится в основной таблице с valid_from.

## Таблица дат вмешательства по договорам

Запрос владельца: таблица договоров, упорядоченная по дате необходимости
вмешательства. Источники — окончание договора и индексация. Уточнение 24 ноября:
название «Договоры: требуют внимания», аренда и коммунальные договоры в одном
блоке, сортировка по дате возрастанию до пагинации: сначала просроченные, затем ближайшие предстоящие сроки (окончательное уточнение 24 ноября). Фильтры «Действие» (Индексация,
Продление договора) и «Тип договора» (Аренда, Коммуналка) объединяются с поиском.
Строка открывает модальное read-only представление; действия доступны по прежним
правам. Подписанная аренда — существующее меню трёх действий; черновик и
коммунальный договор — переход к изменению. «Открыть реестр» убрана.

Подтверждено интервью:
1. Каждое событие — отдельная строка. Если у договора есть обе даты, две строки;
   при совпадении дат обе строки сохраняются.
2. Просроченные события тоже включаются; порядок — дата ASC, ближайшая дата реагирования сверху.

3. Только события, ещё требующие действия. Выполненная индексация исчезает;
   окончание с оформленным следующим договором на том же Space исчезает.

Выполнение индексации фиксирует действие «Индексация»: last_indexation_date
в contracts и зеркальной contracts_history. Простое редактирование суммы,
планирование даты и прочтение уведомления не означают выполнения индексации.
При периодичности показываем первый невыполненный следующий срок, не пропуская
просроченные; календарные месяцы ограничиваются последним днём короткого месяца.
Аннулирование считается обработанным окончанием; отменённый до начала следующий
договор не закрывает окончание предыдущего. Истечение даты само по себе не
означает выполнение действия. Новая запланированная дата индексации отличается
от последней выполненной и снова попадает в список.

У старых договоров факт выполнения неизвестен: миграция оставляет поле NULL,
не восстанавливая его догадкой по изменению суммы или истории.

## Интерфейс объектов, счётчиков и списков: 22 ноября

В объекте одна вкладка «Коммуналка» с поставщиками и их счётчиками. Приборы без поставщика доступны в реестре счётчиков, но не добавляются отдельной строкой в коммуналку. Поставщики без приборов сохраняются в таблице. Зелёный бейдж прибора — показания переданы; оранжевый — подошло окно передачи за 7 дней, есть просрочка либо требуется поверка; до окна без показаний — нейтральный. Просроченная поверка имеет приоритет над переданными показаниями.

Помещения показывают дату окончания текущего договора (при его отсутствии — будущего/последнего), учитывая аннулирование. Цвет по активности и невыполненным событиям договора в окне уведомления. Кнопки добавления в таблицах называются «Добавить». Создание возвращает к исходной таблице/вкладке; модальное быстрое создание выбирает запись в родительской форме.

В списке договоров добавлен status: all, active, upcoming, finished, cancelled. Период действия выбирается одним календарём диапазона: договор попадает в список при пересечении его аренды с выбранным периодом хотя бы на один день, границы включены. Окончание учитывает более раннюю дату аннулирования; отменённые до начала аренды договоры не имеют периода действия. API сохраняет имена expiryFrom/expiryTo для совместимости, но фильтрует пересечение периодов. Форма показаний принимает дату без времени; API и прежние показания сохраняют точность времени, новые значения отправляются с 00:00:00.

Небольшие статичные справочники, объекты и помещения хранятся в Pinia на время сеанса, без persistence. Неполные страницы не кэшируются. Кэш очищается при изменениях, смене сеанса и календарного дня. Оперативные данные счётчиков/договоров/показаний загружаются заново.

## Договоры коммунальных поставщиков: согласовано 22 ноября

Отдельный договор связывает объект и поставщика, может охватывать несколько коммуникаций. По одной паре объект/поставщик допускается несколько договоров, прежние сохраняются. Минимальные реквизиты: номер, дата, обязательное «Действует до» (expiry_date). Номер и дата не отмечены обязательными. Реализовано отдельной сущностью UnityProviderContract; ObjectUnityProvider остаётся связью объекта, коммуникации и поставщика, не договором.

Договоры коммунальных поставщиков также порождают уведомление юристам о предстоящем продлении за один календарный месяц до expiry_date. Применяются общие правила уведомлений: активные незаблокированные пользователи с ролью юриста, защита от повторной генерации, дата исполнения равна дате истечения договора для отображения в календаре. Генератор подключён вместе с UnityProviderContract. Настраиваемые days заменяют прежний календарный месяц, как уточнено ниже.

## Окончательные настройки уведомлений и стартовые таблицы: 22 ноября

notification_types хранит пять полей: id INT PK, name TEXT, days INT >= 0, roles JSONB (массив ролей), is_active BOOLEAN. Типы связаны с системными генераторами по неизменяемому ID. Начальные значения 30/30/7/30 дней для окончания аренды, индексации, показаний, окончания договора коммунального поставщика; роли юрист/юрист/технарь/юрист. Все включены. Ноль дней — в день события. Настройки могут просматривать и изменять только администраторы и директор. Два блока стартового экрана по эскизу доступны юристу, директору и администраторам: все действующие договоры аренды (объект/арендатор/площадь/аренда/окончание/индексация/%), и договоры коммунальных поставщиков (объект/поставщик/статус/оборудование/следующая поверка). Списки упорядочены по объекту и постраничны. Поставщики без оборудования отображаются без вымышленных показаний и поверок.

У договора поставщика добавлен is_suspended: это приостановка договора. Срок истечения продолжает контролироваться, даже если договор приостановлен. Модель, миграции, API, список/редактирование и уведомление о продлении реализованы. Прежние договоры остаются отдельными записями; изменения реквизитов архивируются.

Веб-маршруты переведены на /contracts/1 вместо /#/contracts/1. Прямое открытие и перезагрузка обслуживаются Nginx/Symfony fallback. Старые ссылки поддерживаются нормализацией. Для будущего нативного Capacitor используется hash-router.

## Финансовый блок: ответы интервью 1–3

- Начало финансового учёта — декабрь 2026 года. За месяцы до декабря 2026 начисления не создавать, начальное сальдо нулевое.

- При изменении ежемесячной арендной платы в текущем месяце начисление этого месяца остаётся по прежней сумме; новая сумма применяется со следующего месяца. Не разбивать текущий месяц по старой и новой сумме. Это правило расчёта начислений; фактическое время сохранения версии договора valid_from остаётся прежним согласованным механизмом. Ручные директорские корректировки действуют отдельно по уже согласованным правилам.

## Финансовый блок: ответы интервью 4–6

- Первый расчёт по новому договору выполнять сразу после сохранения, а не ждать следующего 1-го числа. Исключение (ответ 9): при начале аренды в будущем месяце начисление формировать только 1-го числа месяца начала аренды.
- При начале аренды после 5-го числа неоплаченная сумма первого месяца становится задолженностью через пять календарных дней от начала аренды: 20 декабря → 25 декабря. Для прочих месяцев сохраняется правило задолженности с 5-го числа.
- Распределение сумм платежей по периодам выполняет бухгалтер вручную. Автоматический зачёт в старый долг/аванс не реализовывать. Один платёж хранится как один факт внесения денег; разнесение по периодам не создаёт отдельных фактов оплаты. Неразнесённый остаток можно сохранить и распределить позже (ответы 7–8).


## Подписание договора: уточнение 22 ноября

- Contract.isSigned / contracts.is_signed — признак подписания. При создании в интерфейсе чекбокс установлен. Неподписанный договор редактируется без архивации черновых версий и не получает начислений аренды.
- Подписание необратимо: true → false запрещено в API и БД. Первое подписание не архивирует черновик; дальнейшие изменения подписанного договора сохраняются по прежнему механизму истории.
- Подписывать договор могут юрист и администратор, включая суперадминистратора. Администратор имеет все предметные права остальных ролей без назначения ему каждой роли отдельно. Неподписанный договор резервирует площадь Space сразу при создании, включая время до начала аренды. Подписание не создаёт повторный резерв и не меняет занятую площадь; отдельной таблицы резервов по-прежнему нет. До подписания разрешено менять объект и площадь при соблюдении остальных проверок, включая запрет отрицательного остатка площади.


## Финансовый блок: ответы интервью 7–9

- Один платёж — один факт внесения денег. Сохранять историю фактических поступлений, не дробить платёж на фиктивные поступления при разнесении по периодам.
- Платёж разрешено сохранить с неразнесённым остатком; бухгалтер распределяет его позже вручную. Автоматического распределения нет.
- Если договор оформлен сейчас, а аренда начинается в будущем месяце, первое начисление формируется 1-го числа месяца начала аренды. Например: договор оформлен в декабре, аренда начинается в январе — начисление 1 января. Неполный месяц рассчитывается по ранее согласованным фактическим дням.
- Это согласование финансового блока; подписание, резерв и изменение объекта/площади черновика согласованы отдельно ниже.

## Изменение помещения неподписанного договора: согласовано 22 ноября

- До подписания юрист и администратор могут менять объект и площадь помещения через основную форму договора. После подписания объект и площадь неизменны.
- Свободная площадь после сохранения не может быть отрицательной. Это уточнение заменяет прежнее разрешение превышения площади из ответа 36. Нулевой остаток допустим; NUMERIC сравнивается точно, без округления.
- При изменении резерв пересчитывается без двойного учёта текущего договора. При переносе освобождается площадь исходного объекта и резервируется на новом; арендодатель черновика определяется новым объектом.
- Если Space связан только с этим черновиком, корректируются его текущие объект и площадь. Если Space используется другими договорами, для изменяемого черновика выделяется новый Space; прежние договоры сохраняют прежнюю площадь и объект. Пересечения и разрывы оставшейся цепочки запрещены, как ранее согласовано.
- Недостаток площади отклоняет всю операцию: договор, Space, резерв и история остаются прежними. Объекты блокируются в порядке ID, проверки и изменения выполняются в одной транзакции. Уменьшение общей площади объекта ниже занятой также запрещено.
- Новое чтение GET /api/objects/{id}/availability?contractId=... используется формой для точной предварительной проверки и не кэшируется в сеансе. Исключается резерв договора, а не весь Space, который могут резервировать другие договоры. Окончательная проверка выполняется сервером при сохранении.
- Изменения неподписанного договора по-прежнему не архивируются. Правила версий Space и сохранения исторических записей не отменены.


## Позднее подписание и еженедельные напоминания: уточнение 22 ноября

- Если аренда начинается 1-го числа, а договор подписан после 5-го числа того же месяца, начисление должно быть за полный месяц. Не обрезать расчётный период датой подписания и не применять пропорцию только за дни после подписи. Получатели, интервал и включение/выключение задаются настройками notification_types. Для нового типа id=5 days означает интервал повторения (по умолчанию 7, минимум 1), а не срок предупреждения до события. Начальные roles: ROLE_LAWYER, ROLE_DIRECTOR.

Недельный период имеет отдельный ключ дедупликации; прочтение не мешает сообщению следующего периода. При пропуске генерации создаётся только актуальное напоминание, без пачки за прошлые недели. Подписанные, ещё не начавшиеся, отменённые и завершённые договоры исключены; ранее созданные сообщения сохраняются. - На маленьких экранах виджет потребления идёт первым, перед остальными блоками. На больших — справа с обтеканием: нижние блоки используют полную ширину после окончания виджета. Поведение едино для карточки и модального превью.
- Подсказка при наведении на дугу содержит только месяц, год, расход и единицу измерения, например «ноябрь 2026 — 43 кВт·ч». Не добавлять даты интервала или другой текст без указания владельца.


### Навигация сущностей: уточнение 23 ноября

- Основной маршрут записи и переход из строки её реестра открывают форму редактирования с прежними проверками прав. Нередактируемое представление показывать только в явно указанных владельцем местах, преимущественно модально для сторонней сущности. Не подменять им основной маршрут и не менять структуру меню.
- Счётчик: /meters/:id — форма с вкладками; /meters/:id/edit перенаправляет на основной адрес с сохранением query. В «Коммуналке» объекта бейдж открывает модальное превью; его кнопка «К счетчику» ведёт на основной маршрут. Возврат и сохранение используют исходный returnTo, без промежуточной страницы просмотра.


### Коммуналка: договоры и ввод показаний, 23 ноября

- Колонки в порядке владельца: Коммуникация, Поставщик, Номер, Дата окончания, Статус, Счетчик. Все договоры, включая завершённые, каждый отдельной строкой по коммуникации. Договор, охватывающий несколько коммуникаций, отображается у каждой из них. Поставщики без договора остаются; счётчики без поставщика не образуют строки в коммуналке и остаются доступными в реестре приборов.
- Рядом с бейджем счётчика — действие ввода показаний в общей модальной форме для технаря/администратора. На desktop текст «Показания» без иконки; на мобильном — компактная иконка. Бейдж по-прежнему открывает модальное превью, клики действий не вызывают переход по строке. После записи обновляются данные, фильтры и страница сохраняются.


### Логические элементы интерфейса

- Логические фильтры таблиц оформлять переключателями Tabler (form-switch). Логические значения в формах создания/редактирования задавать обычными галочками (form-check), без переключателя.
- В «Коммуналке» фильтры поставщика, коммуникации, статуса договора и «Со счетчиком» применяются совместно. По умолчанию статус «Все статусы», переключатель выключен. При включении показываются только строки с установленными счётчиками. Сброс очищает все фильтры и возвращает первую страницу.


### Вкладка арендаторов объекта: 23 ноября

Вместо таблицы помещений — «Арендаторы» (старый tab=spaces сохраняется). Колонки стартовой таблицы «Действующие договоры аренды» без объекта: арендатор, площадь, аренда в месяц, конец договора, индексация, % индексации. Все договоры, включая завершённые и черновики. Сортировка по ближайшей невыполненной дате вмешательства, просроченные первыми; завершённый без перезаключения не опускается по статусу. Договоры без событий идут в конце, при равенстве — ID DESC. Каждый договор один раз, пагинация после сортировки. Общие события с ContractInterventionService. В строке прежняя кнопка действий с договором для юриста/администратора.

В таблице аренды даты, требующие внимания, выделять оранжевым бейджем. Для окончания/индексации использовать невыполненные события и активное окно days из настроек уведомлений, включая просрочку; выполненные события не выделять.

Виджет площади объекта находится на вкладке «Основное»: над формой на всех размерах экрана. Во вкладке «Арендаторы» виджет не показывается; кнопка «Обновить» не возвращается. Кольцевой график в стиле Traffic sources Tabler: занято зелёное, свободно оранжевое; значения в м² из availability API, включая резерв. Общая площадь в центре. Добавление договора и пагинация остаются доступными.

### Счётчики объекта и межповерочный интервал: уточнение 23 ноября

### Возврат из форм: правило 24 ноября

Во всех самостоятельных формах реестров и справочников нижняя кнопка возврата называется «К списку» и расположена справа; сохранение и другие действия слева. Сохраняется исходная таблица и её вкладка из returnTo, иначе используется список сущности. Модальная «Отмена» продолжает закрывать окно. Формы авторизации и активации не получают несуществующего списка.

### Стартовые договоры и read-only карточки: 24 ноября

В «Действующих договорах аренды» добавлены прежние действия, как на вкладке арендаторов объекта, с обновлением списка после выполнения. Клик строки со старта открывает read-only превью договора. Для обоих видов договоров согласован общий модальный сценарий просмотра с переходом «К договору»; редактирование на основном маршруте сохраняется.

В коммунальных договорах со старта нет «Добавить». Колонки: объект, коммуникация, поставщик, номер, дата окончания, статус, счётчики с модальным просмотром и «Показания». Договор с несколькими коммуникациями показывает их в одной ячейке. Фильтры: поставщик, коммуникация, статус и switch «Со счетчиком», без обязательности и кнопок добавления. Фильтры применяются на сервере до count/пагинации; наличие прибора проверяется для того же объекта, поставщика и выбранной коммуникации. Прежнее отображение общего реестра поставщиков сохраняется.

### Уточнение привязки коммуналки: 24 ноября

Последнее уточнение: на помещении/договоре аренды только счётчики. Контекстная форма содержит коммуникацию и селект свободных приборов этой коммуникации с первым пунктом «Без счетчика» и стандартным модальным созданием. Объект/помещение фиксированы контекстом. Для установки требуется выбрать прибор; отдельная коммуникация помещения без прибора не создаётся. У аренды может быть несколько приборов.

В коммуналке объекта договор содержит одного поставщика, одну коммуникацию и необязательный meterId. Новое поле meter_id добавляется в unity_provider_contracts и зеркальную историю. Сохранение договора и установка атомарны; смена/снятие/перенос прибора очищает прежнюю текущую связь, архив сохраняется. Старые коммуникации и места установки не угадываются миграцией. Непривязанные к договору старые приборы остаются отдельной строкой коммуналки.

Права прежние: договор изменяют юрист/администратор; установка требует администратора или технаря. Для смены прибора из формы договора нужны оба права. Выбор занятого прибора и неправильной коммуникации проверяются сервером под блокировкой.
