# Требования LandLordService

Источник: описание владельца проекта от 19 ноября 2026 года.
Это фиксация запроса, а не утверждённая схема данных.

## Подтверждено пользователем

- Есть несколько объектов недвижимости с торговыми или офисными зданиями.
- По уточнению заказчика фиксированных помещений на объекте нет. `Space`
  выделяется из общей площади объекта для аренды. Состав полей и вопросы
  по новой модели: [domain-model-review.md](domain-model-review.md).
  Уточнение 34–36 заменяет прежнее правило занятости только по датам договоров:
  Space создаётся вместе с первым договором и сразу резервирует площадь,
  даже если начало аренды впереди. При перезаключении Space сохраняется,
  при расторжении становится неактивным. По уточнению 37–39 резерв снимается
  на следующий день после окончания без нового договора или расторжения;
  перезаключение на прежнем Space возможно только без перерыва.
- Коммуникации могут иметь приборы учёта. Нужно вносить показания, рассчитывать
  потребление и вести график передачи показаний. Ответы 56–57: разница показаний
  за фактический интервал без искусственной разбивки пропущенных месяцев.
  На текущем этапе только потребление, без тарифов, стоимости и коммунальных начислений.
- Есть поставщики коммунальных услуг и договоры с ними.
- Несколько собственных юридических лиц выступают владельцами или
  субарендаторами и оплачивают коммунальные и прочие услуги объектов.
- Есть договоры аренды. Контролируем сроки и планируем повышение арендной платы.
  Продления и история индексаций не нужны: вместо старого договора создаётся новый.
  Юрист может аннулировать договор указанной датой.
- Арендаторы: юридические лица, ИП и физические лица.
- Нужен реестр договоров по объектам и датам истечения.
- Сальдо аренды — по каждому договору и суммарно по арендатору.
  Уточнение 52: импорт выписок пока отложен целиком. Бухгалтерия вводит платежи
  вручную в конкретный договор через интерфейс, в том числе задним числом.
  При возвращении импорта в объём работ потребуется идемпотентность.
- Арендную плату начисляем в этой системе. Формулы, периоды и другие правила
  начислений согласуются поэтапно. Все договоры авансовые: 5-го числа текущего
  месяца неоплата по действующим договорам становится задолженностью.
  Ответы 58–60: директор задаёт итоговую сумму к оплате за месяц, включая 0
  (каникулы), не дельту. В интерфейсе — скидка, каникулы или корректировка.
  Базовый неполный месяц начисляется пропорционально дням аренды по фактическому
  числу дней в месяце — правило окончательно подтверждено, не предварительное.
  Директор может корректировать любые параметры начисления, включая прошедшие
  и оплаченные месяцы. Изменение начисления меняет сальдо; платежи при этом
  автоматически не переписываются. Итоговое начисление округлять один раз в конце до копеек по
  математическому правилу (HALF_UP), без промежуточного округления дневной ставки. Например, 100,005
  → 100,01. Импорт выписок отложен.
- Для начислений подготовлена contract_accruals и отдельная
  contract_accruals_correction для директорских корректировок. Схема согласована,
  SQL включён в предметные миграции; сервис расчёта ещё не реализован. У начисления может быть несколько корректировок;
  актуальны параметры и итоговая сумма последней записи, включая 0.
  Без корректировок применяется исходное начисление. Корректировки не складываются
  и не являются дельтами. Последняя определяется порядком создания
  (created_at DESC, id DESC); пересчёт базы не затирает её.
- Бухгалтерия заносит платежи, технические сотрудники вносят показания,
  юрист ведёт договоры, администратор имеет полные права, директор смотрит
  аналитику. Один пользователь может совмещать несколько ролей.
- Backend: Symfony, PHP, Nginx, PostgreSQL в Docker.
- Web: адаптивный mobile-first интерфейс с перспективой Android на Capacitor.
- Нужны бесплатная UI-панель, календарь, таблицы и автокомплиты.
- Начальный дизайн выполняется после согласования UI-панели.
- Панель согласована: основной интерфейс на Tabler + Vue + Symfony API.
  Этот же Vue-клиент будет использоваться в Android-приложении через Capacitor.
  Часть функциональности будет на Tabler + Twig; конкретные разделы не определены.
- Концепции и бизнес-правила определяет пользователь.

## Открытые решения

1. UI: конкретные бизнес-разделы на Twig и границы их мобильной доступности
   нужно определить по мере разработки. Архитектура и панель согласованы.
2. Импорт выписок пока вне текущего объёма: ввод платежей ручной по договорам.
   Формат и образцы потребуются только при отдельном возвращении задачи импорта.
3. Начисления аренды выполняются в системе, начинаем с нулевого сальдо.
   Бухгалтерия вводит платёж в конкретный договор; пользователь исправляет
   собственную запись, удалять платёж может только администратор.
   Округление согласовано: итог до копеек, HALF_UP, один раз в конце;
   промежуточная дневная ставка не округляется.
4. Договоры: уточнить цепочку собственник → арендатор → субарендатор,
   роли собственных юрлиц и стороны каждого вида договора.
5. `Space` выделяется из площади объекта; договор содержит `spaceId`.
   Площадь резервируется сразу при создании Space с первым договором. Пересечения периодов договоров одного
   Space запрещены, включая общий день окончания/начала. При изменении площади
   создаются новые Space, прежние сохраняются для истории. При обычном
   перезаключении договора Space остаётся; при расторжении становится неактивным.
6. Аренда: как задать ставку, периоды, сроки платежей, индексацию,
   перерасчёты? Начальное сальдо пока нулевое. Обеспечительный платёж только реквизит,
   без отдельного учёта движения и зачётов.
7. Учёт ресурсов: где установлены счётчики, есть ли общие/вложенные приборы,
   тарифные зоны, замены и сбросы; что делать с помещениями без счётчиков?
8. Коммунальные услуги: сейчас только потребление по показаниям. Тарифы,
   стоимость, коммунальные начисления и распределение не входят в текущий объём.
9. Доступ: права только по операциям или также по объектам и юридическим лицам?
10. Календарь: сроки и события или также дорожки по помещениям/объектам?
11. Мобильный клиент: понадобится ли работа без сети? Сам Capacitor
    не определяет правила офлайн-ввода и разрешения конфликтов.

Вопросы уточняются по мере работы над соответствующим модулем.
20 ноября схема согласована. Пять предметных миграций на 20 таблиц находятся
в `backend/migrations/domain`, зарегистрированы в Doctrine и применены
к локальной development-БД через миграции. Реализованы ORM всех таблиц и API/интерфейс объектов и арендодателей;
остальные предметные API и расчёты пока не реализованы.
Сервер при создании объекта подставляет reading_day = 25, при создании договора —
тип «аренда». Оба столбца обязательны в БД и не имеют SQL DEFAULT.

## Технические предложения, требующие предметного уточнения

- Идемпотентность должна учитывать повторный файл и повторные операции
  в разных выписках с пересекающимися периодами. Хеша файла недостаточно.
  Ключ банковской операции и обработка исправлений зависят от образцов.
- Сальдо складывается из начислений и ручных платежей по договору; начальное
  сальдо на текущем этапе нулевое. Пользователь исправляет собственную запись
  платежа, удаляет платёж только администратор. Автор платежа сохраняется
  для проверки прав. Начальные долг/переплата пока не вводятся.
- Роли можно совмещать. Ограничения на чтение, изменение и объекты ещё
  не определены; перечисленные роли не являются готовой матрицей доступа.

## Пользователи и доступ: согласовано

- Основной идентификатор пользователя: email.
- При создании обязательны имя и email; остальные поля необязательны.
- Дополнительные поля: фамилия, аватар, телефон, должность и набор ролей.
- Роли можно совмещать: администратор, бухгалтерия, технарь, юрист, директор.
  Индивидуальные разрешения поверх ролей пока не нужны.
- Вход через API с Bearer-токеном. Открытой регистрации нет.
- Открытые экраны: вход, запрос восстановления, установка нового пароля.
- Администратор создаёт пользователей по приглашению без задания пароля,
  блокирует обычных пользователей, меняет их email и роли, отправляет ссылки.
- Пользователь по ссылке задаёт пароль и дополняет профиль. Только после
  сохранения учётная запись становится активной. Приглашение можно отправить повторно.
- Обычный пользователь для изменения данных обращается к администратору.
  Администратор меняет свои данные и данные обычных пользователей; изменение
  другого администратора запрещено, включая email, роли, блокировку и аватар.
- Первый администратор: admin@example.com. Пароль задан пользователем отдельно
  и не включается в исходники или документацию.
- SMTP уже есть, его подключение будет отдельной настройкой. Mailpit не добавлять.
- Схему БД и разовые преобразования данных изменять только через миграции.

- Текущая БД тестовая; admin@example.com является техническим тестовым аккаунтом.
- 2FA отложена. Материал сохранён в docs/two-factor-authentication.md.

## Аватар пользователя: уточнение

- Круглый аватар показывает сохранённое фото либо первые буквы имени и фамилии.
- Имя и фамилия добавлены в профиль; для старых записей они могут отсутствовать.
  До их заполнения показывается нейтральный значок пользователя.
- Нажатие на круг открывает выбор изображения. Выбранное фото сохраняется сразу,
  независимо от сохранения остальных полей формы.
- У новой учётной записи фото загружается после её создания.

## Новая предметная модель от заказчика

- Арендодатель — простой справочник `LandLord(id, name)`.
- Первый набор полей объекта: `id`, `square`, `name`, `address`.
  Арендодатель относится ко всему объекту через `landLordId`.
- `Space(id, name, square)` — выделяемая арендуемая часть объекта.
  Вводятся площадь и реквизиты договора, графический план не нужен.
  name по умолчанию генерируется из площади и Renter.name арендатора,
  например «100 кв.м ИП Иванов И.И.». Используется имя арендатора, не арендодателя.
  Пользователь может изменить название вручную; сохраняется введённое им значение.
- Тип договора — обязательный справочник ContractType(id, name), ссылка
  contractTypeId (contract_type_id). Начальные записи: «аренда» (по умолчанию),
  «юр.адрес». Записи создаёт миграция. Оба типа связаны со Space и занимают площадь.
- У договора указаны `id`, `spaceId`, `renterId`, `securityPayment`, `expiryDate`,
  `contractDate`, `contractNum`, `monthlyPayment`, `increaseDate`, `increasePercent`.
  `contractDate` — начало аренды. Добавлено необязательное `annulmentDate` для
  аннулирования указанной датой; дата подписания не требуется.
  В интервью подтверждено: expiryDate обязательна, бессрочных договоров нет.
  increaseDate и increasePercent могут быть NULL только одновременно;
  если индексация задана, заполнены оба поля. securityPayment может быть 0,
  отсутствие обеспечительного платежа не обозначается NULL.
  monthlyPayment — сумма за весь Space за месяц, не ставка за м².
  Арендная плата и обеспечительный платёж — только в рублях.
  Смена арендодателя объекта влечёт перезаключение договора.
  Номер договора справочный, может повторяться; к одному договору нужны
  несколько файлов любых типов до 20 МБ каждый. Исторические договоры,
  Space и показания физически не удаляются. Удалять вложения договора могут
  юрист и администратор.
  Разрешена отмена до начала аренды с сохранением договора
  в истории: он никогда не занимает площадь и не блокирует другие договоры.
- Тип арендатора — отдельный справочник `Ownership(id, name)`; у Renter
  предусматривается обязательная ссылка ownershipId (ownership_id).
  Начальные записи: «Юридическое лицо», «Индивидуальный предприниматель»,
  «Физическое лицо»; заполняются миграцией.
- `Renter`: `id`, `name`, необязательный `inn`. Арендатора можно создать до
  получения ИНН. После заполнения ИНН должен быть уникальным среди арендаторов;
  отсутствие хранится как NULL. Ответ 18 заменяет прежнюю обязательность ИНН.
  `RenterContact`: `id`, `renterId`, обязательное `name`,
  необязательные `lastName`, `patronymic`, `phone`, `email`.
  Контакт допустим без телефона и email.
- `Unity`: `id`, `name`, `useMeter`, необязательная единица измерения (добавлена по интервью).
  useMeter (use_meter) — возможность установки счётчика: без признака поле
  счётчика не показывается; с признаком доступно. Обязательность установки не задаётся.
  Признак разрешено выключать при существующих счётчиках; приборы, данные
  и связи сохраняются. Задания по показаниям по-прежнему зависят от установки.
  `UnityProvider`: `id`, `unityId`, `name`;
  `ObjectUnityProvider`: `id`, `unityProviderId`, `objectId`.
  На объекте допускается несколько поставщиков одного типа коммуникации.
- `Meter`: `id`, `utilityId`, `createDate`, `startRead`, `verificationDate`,
  `verificationIntervalDays`, необязательный справочный `serialNumber`.
  `createDate` — вручную заполняемая дата производства и дата начальных показаний,
  не дата добавления записи в БД. verificationIntervalDays обязателен; показания целые.
  verificationDate — необязательная последняя поверка. При NULL прибор считается
  новым: базой служит createDate. Срок = база + verificationIntervalDays дней.
  Если текущая дата позже срока, прибор невалиден, но его установку разрешаем.
  Постоянное предупреждение в интерфейсе сохраняется до действующей поверки;
  статус вычисляется по датам, отдельный флаг валидности не хранится.
  У счётчика не более одной установки: объект либо Space. При снятии связи
  очищаются, прибор и показания сохраняются. Задания на передачу показаний
  нужны только при наличии установки в момент передачи. Флаг активности
  не вводится. Это уточняет ответ 33. Счётчики независимы, иерархия не нужна.
  Храним только текущее место установки, без истории перемещений.
  История всех поверок нужна: запись содержит id, ссылку на счётчик и дату поверки.
  Комментарий, номер свидетельства и файл поверки не нужны.
- `ObjectMeter` и `SpaceMeter`: `id`, необязательный `comment`, `meterId`.
  В интервью подтверждены `Space.objectId`, `ObjectMeter.objectId` и `SpaceMeter.spaceId`:
  каждый Space принадлежит ровно одному объекту, установки указывают объект или Space.
  Связь объекта с арендодателем подтверждена ранее.
- `MeterReading`: `id`, `meterId`, `meterReadingDate`, `meterRead`.
  Уменьшение показаний запрещено; ввод задним числом и исправление ошибочного
  показания разрешены. Проверять порядок значений относительно соседних записей
  по времени и начального показания. На прибор и момент снятия одно актуальное
  показание. Ошибку исправляют в существующей записи, историю исправлений не хранят.
- График передачи показаний ежемесячный, общий на уровне объекта для его приборов
  и приборов Space. По умолчанию — 25-е число месяца. У отдельного счётчика можно
  задать собственный срок; без него используется график объекта.
- Денежные суммы хранятся в `NUMERIC`; площади и процент также переведены
  на точное десятичное хранение без заданного масштаба. Ответом 61 согласовано
  округление итогового начисления до копеек один раз в конце по HALF_UP,
  без промежуточного округления дневной ставки. Подробности в [разборе модели](domain-model-review.md).
- Поставщики пока остаются с исходными полями, без реквизитов договоров.
- Уточнение 34–36: Space и первый договор создаются совместно, площадь
  резервируется сразу, включая период до начала аренды. При перезаключении
  используется прежний Space; при расторжении он становится неактивным.
  square объекта — полностью сдаваемая площадь. Превышение допускается,
  жёсткая блокировка не согласована.
  Уточнение 37–39: резерв автоматически освобождается на следующий день после
  окончания без нового договора или после даты расторжения; сама конечная дата
  включена в аренду. Будущее расторжение не освобождает площадь сразу.
  Прежний Space сохраняется только при перезаключении без перерыва;
  после освобождения для новой аренды создаётся новый Space.
  Пересечения периодов договоров одного Space по-прежнему запрещены.
  При изменении площади создаются новые Space, прежние сохраняются для истории.
  Это заменяет прежнее правило остатка исключительно по датам действия.
- Отдельная таблица резервов не нужна. Сданная площадь — сумма площадей Space
  по текущим договорам, свободная — objects.square минус эта сумма.
  Один Space учитывается один раз по ID, исторические и следующие договоры
  его площадь повторно не добавляют. Первый договор с будущим началом тоже
  учитывается сразу после совместного создания с Space.
  Общая площадь объекта физически не уменьшается.
- Сейчас задача ограничена анализом и подготовкой миграций. Реализация
  обсуждается отдельно 20 ноября; сроки не назначены.

## Реализованный реестр объектов

- Предметные названия одинаковы на PHP и TypeScript: RentalObject, LandLord.
- Администратор и юрист создают и редактируют объекты и арендодателей;
  остальные авторизованные пользователи просматривают.
- Список с поиском и пагинацией; карточки на отдельных маршрутах.
- Обязательные название, адрес, положительная точная площадь, арендодатель;
  день показаний 1–31, серверное начальное значение 25.
- Валидация на клиенте и сервере; арендодатель выбирается через поиск.

## Уточнения интерфейса объектов от 20 ноября

- Быстрое создание арендодателя — кнопкой справа от селекта в модальном окне.
  Форма общая с отдельной страницей; созданная запись сразу добавляется и выбирается.
  Данные объекта и текущий сеанс сохраняются, новая вкладка не открывается.
- В поле площади используется IntInput, допускающий только цифры. Некорректный
  ввод отклоняется без склеивания цифр по разные стороны разделителя.
- При создании объекта день показаний не вводится, сервер задаёт 25. Настройка
  графика вынесена в блок приборов учёта существующего объекта и сохраняется отдельно.
