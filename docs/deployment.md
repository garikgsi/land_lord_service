# Публикация Land Lord Service на Docker-сервере

Скрипт [bin/deploy](../bin/deploy) запускается **на сервере**, из подготовленной
копии проекта. Нужны Docker Engine с Compose v2 (поддержка `up --wait`),
доступ к Docker daemon, интернет для первой сборки и POSIX shell.
PHP, Composer, Node.js и PostgreSQL на хост устанавливать не нужно.
Git нужен, если исходники доставляются через репозиторий.

Это публикация на один сервер с коротким перерывом во время резервного копирования,
миграций и переключения контейнеров. Скрипт собирает текущие файлы проекта,
не выбирает ветку, не делает pull, commit или push. Коммит выполняется агентом
только после явной приёмки изменений либо прямого поручения владельца.

## Файлы и данные

- `Dockerfile.production` — сборка Vue, production PHP без dev-зависимостей,
  Nginx со статическими ресурсами. Исходники не монтируются с сервера.
- `compose.production.yaml` — самостоятельная конфигурация, используется
  **без** development-файла `compose.yaml`.
- `.env.production.example` — пример настроек без секретов.
- `.env.production` — локальные настройки сервера, исключены из Git и Docker context.
- `var/production/postgresql` — данные PostgreSQL; у PostgreSQL 18 кластер
  расположен внутри `18/docker`.
- `var/production/avatars` — загруженные аватары.
- `var/production/backups/<UTC-время>-<PID>` — копия БД в формате pg_dump,
  архив аватаров и список образов работающих контейнеров.
- `var/production/deploy.lock` — защита от параллельных запусков скрипта.

Данные разработки `var/postgresql` и `backend/var/avatars` не используются.
Новые хранилища файлов, когда они появятся в реализации, нужно добавить
в production volumes и резервное копирование. Сейчас загрузка файлов договоров
ещё не реализована.

## Первый запуск

1. Доставьте на сервер **принятую версию** проекта. Например, после её публикации
   в вашем Git-репозитории:

   ```sh
   git clone <URL-репозитория> /srv/landlordservice
     cd /srv/landlordservice 
   git checkout <принятый-тег-или-коммит>
   ```

   Можно также загрузить файлы без Git. Не переносите локальные `.env`,
   `var/`, `backend/var/`, `backend/vendor/`, `frontend/node_modules/`
   и `frontend/dist/`: зависимости и клиент собираются в Docker.

2. Создайте серверный файл настроек:

   ```sh
   cp .env.production.example .env.production
   chmod 600 .env.production
   ```

   Заполните его текстовым редактором:

   | Переменная | Значение |
   | --- | --- |
   | COMPOSE_PROJECT_NAME | Уникальное постоянное имя, например landlordservice-prod |
   | HTTP_BIND | 127.0.0.1 для reverse proxy на том же сервере |
   | HTTP_PORT | Свободный локальный порт, по умолчанию 18081 |
   | APP_SECRET | Случайная hex-строка, минимум 32 байта |
   | POSTGRES_DB | Имя production-базы |
   | POSTGRES_USER | Пользователь PostgreSQL |
   | POSTGRES_PASSWORD | Отдельный случайный пароль в hex-формате |
   | APP_FRONTEND_URL | Публичный адрес, например https://rent.example.com |
   | MAILER_DSN | Реальный SMTP DSN |
   | MAIL_FROM | Адрес отправителя, разрешённый SMTP-провайдером |

   Если на сервере есть OpenSSL, сгенерируйте два разных значения:

   ```sh
   openssl rand -hex 32
   openssl rand -hex 24
   ```

   Первое вставьте в APP_SECRET, второе — в POSTGRES_PASSWORD.
   Для пароля БД используйте hex: он вставляется в DATABASE_URL без дополнительного
   URL-кодирования. Имя БД и пользователя задавайте буквами, цифрами и символом `_`.
   SMTP-логин и пароль с особыми символами URL-кодируйте в DSN.
   Не меняйте POSTGRES_PASSWORD у существующей БД простым редактированием файла:
   PostgreSQL не обновляет пароль роли при повторном запуске контейнера.

   Пример SMTP: `smtp://USER:URL_ENCODED_PASSWORD@smtp.example.com:587`.
   Для тестового стенда допустимо `null://null`, но письма тогда не отправляются.
   APP_ENV=prod и APP_DEBUG=0 зафиксированы в production Compose.

3. Проверьте настройки и запустите публикацию:

   ```sh
   ./bin/deploy --check
   ./bin/deploy
   ```

   Это основной вариант: скрипт читает `.env.production` из каталога проекта.
   Если разместить файл там не получилось, сохраните заполненные настройки
   в другом доступном файле, например `/etc/landlordservice/production.env`,
   и явно укажите путь:

   ```sh
   ./bin/deploy --env-file /etc/landlordservice/production.env --check
   ./bin/deploy --env-file /etc/landlordservice/production.env
   ```

   Используется один файл настроек; второй создавать не нужно.
   Этот вариант меняет только расположение настроек и не устраняет другие
   ошибки запуска, например отсутствие доступа к Docker.
   Если выбран другой путь, используйте его и при ручных Compose-командах.
   По возможности запускайте в `tmux` или `screen`, чтобы разрыв SSH
   не прервал миграцию.

4. Инициализируйте системного суперадминистратора. Миграция создаёт неактивный
   аккаунт `admin@example.com`, без пароля. Команда запрашивает пароль скрыто:

   ```sh
   docker compose --env-file .env.production -f compose.production.yaml exec \
     --user www-data php php bin/console app:user:initialize-admin 'Имя администратора'
   ```

   Команда выполняется один раз. Тестовые данные и пароль локального
   администратора автоматически не переносятся.

5. Настройте домен и HTTPS. По умолчанию приложение доступно на сервере по
   `http://127.0.0.1:18081`. PostgreSQL и PHP-FPM наружу не опубликованы.

   Для уже установленного на сервере Nginx добавьте в **HTTPS server-блок**
   вашего домена:

   ```nginx
   location / {
       proxy_pass http://127.0.0.1:18081;
       proxy_set_header Host $host;
       proxy_set_header X-Forwarded-For $remote_addr;
       proxy_set_header X-Forwarded-Proto $scheme;
       client_max_body_size 21m;
   }
   ```

   Сертификат и перенаправление HTTP → HTTPS настраиваются на reverse proxy.
   Приложение сейчас использует APP_FRONTEND_URL для ссылок из писем;
   оно должно совпадать с публичным HTTPS-адресом.
   Если reverse proxy находится в другом контейнере, его `127.0.0.1`
   относится к нему самому: подключите его к нужной Docker-сети либо настройте
   доступ к хосту. Публиковать контейнерную БД для этого не требуется.

## Что делает скрипт

1. Проверяет Docker, Compose и конфигурацию без вывода значений секретов.
2. Устанавливает блокировку параллельного запуска.
3. Собирает образы по lock-файлам: `npm ci`, Vue build,
   `composer install --no-dev --optimize-autoloader`, ресурсы Symfony.
   Ошибка сборки оставляет работающие контейнеры приложения нетронутыми.
4. Запускает PostgreSQL и ждёт готовности.
5. Сохраняет список текущих образов, останавливает Nginx и PHP, чтобы исключить
   запись через приложение во время копирования.
6. Создаёт pg_dump и архив аватаров. Незавершённые копии имеют суффикс `.partial`.
   Даже при первом запуске сохраняется копия начального состояния базы.
7. Настраивает права каталога аватаров и выполняет **все зарегистрированные**
   Doctrine-миграции.
8. Пересоздаёт PHP, очищает и прогревает production cache, запускает Nginx.
9. Ждёт успешного `/api/healthz`, проверяющего также доступ к PostgreSQL.

Операции со схемой выполняются только Doctrine-миграциями. Скрипт не вызывает
schema:update и не сбрасывает базу. Предметные миграции на 20 таблиц уже включены:
первый запуск применит и их. ORM-модели всех 20 таблиц реализованы; проверка schema:validate сверяет их
с миграциями. Ограничения PostgreSQL, включая EXCLUDE периодов договоров,
управляются миграциями; не заменяйте их автоматически сгенерированной схемой.

## Обновления

Доставьте принятую версию файлов в тот же каталог и снова выполните:

```sh
./bin/deploy --check
./bin/deploy
```

Обновление кода выполняется через сборку новых образов, хранилища сохраняются.
Не используйте development-скрипт `bin/setup` на production.
Базовый образ PostgreSQL закреплён в Compose: его major-обновление требует
отдельного переноса данных. Не заменяйте тег версии без процедуры обновления БД.

Проверка состояния и журналы:

```sh
docker compose --env-file .env.production -f compose.production.yaml ps
docker compose --env-file .env.production -f compose.production.yaml logs --tail=100 php nginx
curl --fail http://127.0.0.1:18081/api/healthz
```

## Ошибки и восстановление

Если сборка завершилась ошибкой, исправьте причину и повторите запуск.
Если ошибка возникла после остановки приложения, скрипт оставляет PHP и Nginx
остановленными. Он не запускает прежний код поверх частично изменённой схемы
и не выполняет автоматический rollback БД.

Сначала изучите сообщение команды и резервную копию. Исправляемая ошибка
миграции или запуска обычно позволяет повторить публикацию.
После SIGKILL или выключения сервера может остаться `deploy.lock`:
удалите пустой каталог блокировки через `rmdir var/production/deploy.lock`
только убедившись, что другой deploy не работает.

Для отката нужны **совместно** предыдущие образы/версия кода, дамп БД и архив
аватаров из одного каталога. В `images.txt` записаны идентификаторы прежних
работающих образов; до завершения приёмки не запускайте `docker image prune`.
Дамп проверяется через `pg_restore --list` и восстанавливается `pg_restore`
в отдельную пустую базу. После проверки восстановленных данных переключите
приложение на неё и восстановите соответствующие аватары и код.
Откат миграций командой `down` не заменяет восстановление данных.

Копии на том же диске защищают от ошибочного обновления, но не от потери сервера.
Переносите `var/production/backups` и серверный файл настроек в защищённое
внешнее хранилище. Ротация и регулярные резервные копии между публикациями
настраиваются отдельно; скрипт существующие копии не удаляет.
Если есть внешние клиенты, пишущие прямо в БД, на время резервного копирования
их также нужно остановить.

## Проверка самого скрипта

```sh
sh -n bin/deploy
python3 -m unittest discover -s tests/deploy -v
```

Python нужен только для тестов скрипта, не для публикации.

Подход основан на официальной документации
[Docker Compose для production](https://docs.docker.com/compose/how-tos/production/)
и [публикации Symfony](https://symfony.com/doc/current/deployment.html).
